# Bundle size benchmark

Measures minified, gzip (level 9), and brotli (quality 11) bundle sizes for
ML-KEM and ML-DSA applications, each of which does one operation with one
parameter set. `@webpqc/mlkem` and `@webpqc/mldsa` are bundled from the current
repository sources, and `@noble/post-quantum` is measured the same way for
comparison.

Generated bundles are verified by running them against each other: all key
generation bundles must derive the same key pair from a seed, and every encap
(sign) bundle must interoperate with every decap (verify) bundle, across the
libraries.

## Usage

Requires Node.js >= 24 and npm. The sources are TypeScript, which Node.js runs
directly.

```sh
cd bench/bundle
npm ci
npm run bench
```

Results are written to `results.md` and `results.json`, which are ignored by
Git.

To select suites or a bundler, or inspect module sizes:

```sh
npm start -- --filter mldsa --bundler rollup
npm start -- --filter mlkem768 --bundler esbuild --analyze
```

Each run writes its bundles to a directory of its own, `dist/run-*`, and removes
it afterwards, so runs can be executed in parallel. With `--keep`, the directory
is kept and its path is printed. The parent `dist/` is left in place, and is
ignored by Git.

`npm run bench` always writes to `results.md` and `results.json`, so parallel
runs of it overwrite the reports of each other. Give each parallel run its own
paths instead, and wait for each of them, as a `wait` without a process ID
succeeds even if a run failed:

```sh
npm start -- --filter mlkem --md results.mlkem.md --json results.mlkem.json &
mlkem=$!
npm start -- --filter mldsa --md results.mldsa.md --json results.mldsa.json &
mldsa=$!

status=0
wait "$mlkem" || status=1
wait "$mldsa" || status=1
# Fails if either of the runs failed.
[ "$status" -eq 0 ]
```

Use `npm start -- --help` for all options and `npm run typecheck` to type-check
the tool.

## Suites

Each suite is measured for the roles of its kind. Definitions are in
[`src/suites.ts`](./src/suites.ts), and the application sources are generated by
[`src/libs.ts`](./src/libs.ts).

| Suite ID    | Algorithm   | `@webpqc` package | Roles                        |
| ----------- | ----------- | ----------------- | ---------------------------- |
| `mlkem512`  | ML-KEM-512  | `@webpqc/mlkem`   | `keygen` / `encap` / `decap` |
| `mlkem768`  | ML-KEM-768  | `@webpqc/mlkem`   | `keygen` / `encap` / `decap` |
| `mlkem1024` | ML-KEM-1024 | `@webpqc/mlkem`   | `keygen` / `encap` / `decap` |
| `mldsa44`   | ML-DSA-44   | `@webpqc/mldsa`   | `keygen` / `sign` / `verify` |
| `mldsa65`   | ML-DSA-65   | `@webpqc/mldsa`   | `keygen` / `sign` / `verify` |
| `mldsa87`   | ML-DSA-87   | `@webpqc/mldsa`   | `keygen` / `sign` / `verify` |

- **keygen**: derives a key pair from a seed.
- **encap** / **decap**: encapsulates to a public key, and decapsulates with a
  private key.
- **sign** / **verify**: signs a message with a private key, and verifies the
  signature with a public key.

The `@webpqc` applications create an instance with a factory function of the
parameter set, and the `@noble/post-quantum` ones import the object of the
parameter set (e.g. `ml_kem768`).

| Package         | Role                         | Factory function (e.g.)   |
| --------------- | ---------------------------- | ------------------------- |
| `@webpqc/mlkem` | `keygen` / `encap` / `decap` | `createMlKem768()`        |
| `@webpqc/mldsa` | `keygen` / `sign`            | `createMlDsa65Signer()`   |
| `@webpqc/mldsa` | `verify`                     | `createMlDsa65Verifier()` |

`@webpqc/mldsa` separates the verifier from the signer, so that an application
which only verifies signatures does not bundle the code for key generation and
signing.

## Bundlers

| Bundler | Configuration                                                                         |
| ------- | ------------------------------------------------------------------------------------- |
| esbuild | Bundle, minify, ESM, target ES2022                                                    |
| Rollup  | `@rollup/plugin-node-resolve` + `@rollup/plugin-terser`, ESM, dynamic imports inlined |

`@webpqc/*` is resolved to `packages/<name>/mod.ts`, with the `sideEffects`
value which the package declares for npm in its `dnt.ts`. `@noble/post-quantum`
and its dependencies are resolved from `node_modules`.
